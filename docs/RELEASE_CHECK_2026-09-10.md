# Локальная проверка релиза — 10 сентября 2026

Этап 2 ближайшей очереди выполнен частично. Среда: Windows, production-сборка Next.js, временная MongoDB на localhost и вымышленные пользователи двух tenant. Рабочая база не использовалась. Внешние провайдеры в HTTP-тестах заменены локальными ответами.

## Результаты

- Production-сборка прошла с двумя workers (`CIRCLE_NODE_TOTAL=3`).
- HTTP-набор с браузером: 23 проверки, 0 ошибок, 0 пропусков. Покрывает mobile auth, tenant isolation, синхронизацию, файлы, контракты интеграций, Public Leads/Tilda, генерацию договора/акта, вход в браузере и восстановление очереди после перезапуска. Web-сценарий использует настоящий вход NextAuth с CSRF и cookie: клиент → заявка → подтверждение → задаток → окончательная оплата → налоги → закрытие.
- Проверены запрет чужого доступа и серверная отдача страниц «Важное», мероприятий и клиентов. Это HTTP-проверки, а не проверка взаимодействия в браузере.
- Реальные `mongodump` и `mongorestore` восстановили синтетический архив в отдельную пустую базу. Совпали документы, BSON-типы, связи и индексы шести коллекций, включая пустую. Проверены SHA-256 копии архива и неизменность исходной базы. Временная среда удаляется после проверки.
- В той же изолированной MongoDB прошла проверка конкурирующего резервирования и возврата бюджета файлового импорта, ранее пропускавшаяся без настроенной БД.

## Исправленная ошибка

API разрешал закрыть неоплаченное мероприятие, хотя интерфейс запрещал это действие. Создание сразу закрытого мероприятия и переход в закрытый статус теперь проверяют оплату; для мероприятия по договору требуется транзакция «Налоги». При нарушении возвращается HTTP 409 с `{ success: false, error }`. Сохраняется запрет незакрытых обязательств. Эти же обработчики используются мобильным API и sync push.

Правки обычных полей старых закрытых мероприятий не требуют пересчёта оплаты; изменение договорной суммы или признака договора проверяется. Дата мероприятия не запрещает ручное закрытие. Правила обработки незавершённых задач не менялись.

Дополнительный прогон обнаружил дублирование клиента между API и Tilda при передаче одного номера как `+7…` и `8…`. Номера теперь нормализуются, а поиск учитывает старые записи с `8` и без кода страны в том же tenant. Существующие дубликаты не объединяются автоматически.

Проверка offline выявила ложное подтверждение сохранения при ошибке localStorage и удаление старых записей при переполнении очереди. Теперь ошибка записи передаётся вызывающему коду и показывается пользователю; заполненная очередь отклоняет новое изменение, сохраняя старые. Повреждённая очередь не перезаписывается. Ошибка сохранения статуса останавливает обработку очереди. Добавлены регрессионные проверки.

Проверка перезапуска обнаружила отсутствие таймера повторной отправки: `nextRetryAt` сохранялся, но очередь могла ждать бесконечно до следующего действия пользователя. Добавлен таймер по ближайшему времени повтора и запуск при изменении очереди. При размонтировании таймер удаляется; при offline и выключенной синхронизации отправка не запускается. Ошибка записи состояния в localStorage останавливает обработку без цикла немедленных повторов.

Также добавлена межвкладочная блокировка replay через Web Locks: localStorage общий, а прежний React ref защищал только одну вкладку. Тест после перезапуска открывает два кабинета одновременно и проверяет одну запись на сервере. Подтверждено в Edge; в браузерах без Web Locks сохраняется прежняя защита внутри одной вкладки, межвкладочная гарантия для них не заявляется.

Offline-сценарий расширен в `tests/web/offlineSmoke.mjs`: отключение сети через Playwright, JSON-запрос создания клиента через действующий fetch-gate страницы, проверка сохранённого тела запроса, возврат сети, очистка очереди и одна запись в серверной БД. Проверяется также отказ localStorage с видимым сообщением об ошибке. Это проверка браузерной очереди через fetch, а не заполнения формы клиента или установленного PWA. При намеренном отключении сети ожидаются сообщения `ERR_INTERNET_DISCONNECTED`, в том числе от Яндекс Метрики. Модульный набор очереди после расширения содержит 7 успешных тестов.

Чтобы включить браузер в HTTP-набор, перед запуском задайте `PLAYWRIGHT_MODULE` — абсолютный путь к `playwright/index.mjs` установленного пакета. Для текущего окружения это `C:/Users/Escal/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules/playwright/index.mjs`. Требуется установленный Microsoft Edge. Без переменной браузерная проверка явно пропускается.

`tests/web/restartSmoke.mjs` закрывает и заново запускает процесс Edge с тем же временным профилем. Содержимое запроса и его идентификатор сохраняются без подстановки storageState; после входа очередь обрабатывается и создаёт одного клиента. В `offlineSmoke.mjs` первая отправка намеренно прерывается до обработки сервером: через backoff повтор проходит автоматически, без ручного действия. Это не проверка аварийного завершения во время уже принятой сервером операции; гарантия отсутствия дублей при потере ответа сервера здесь не заявляется.
