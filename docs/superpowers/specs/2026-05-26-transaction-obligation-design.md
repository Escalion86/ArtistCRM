# Дизайн: метод транзакции «Обязательство»

## Контекст

В ArtistCRM уже есть транзакции с типом (`income`/`expense`), категорией и методом оплаты. Пользователю нужен новый сценарий: завести транзакцию, которой ещё не было фактически, но которая уже финансово запланирована. Типичный пример: обязательство отдать процент организатору после мероприятия.

Такое обязательство должно:

- учитываться в расчётах и статистике как полноценная транзакция;
- явно отображаться в интерфейсе как незавершённое финансовое обязательство;
- блокировать закрытие мероприятия до тех пор, пока транзакция не будет переведена в обычный способ оплаты и не получит фактическую дату совершения.

## Решение

### Модель данных

Добавляется новый метод оплаты транзакции:

- `paymentMethod = obligation`

Это именно новый метод оплаты, а не новый тип транзакции и не новая категория.

Причины выбора:

- не ломает существующую финансовую модель;
- не требует специальных исключений в расчётах сумм и статистики;
- позволяет просто и однозначно находить незакрытые обязательства;
- минимально меняет текущий API и интерфейс.

### Семантика даты

Поле `date` используется по-разному в зависимости от метода оплаты:

- если `paymentMethod = obligation`, `date` означает плановую дату исполнения обязательства;
- если `paymentMethod` любой другой (`transfer`, `account`, `cash`, `barter`), `date` означает фактическую дату совершения транзакции.

При переводе транзакции из `obligation` в любой другой метод оплаты пользователь обязан указать корректную фактическую дату. После сохранения именно эта дата хранится в поле `date`.

### Бизнес-правила

1. Транзакция с методом `obligation` участвует в расчётах и статистике без исключений.
2. Мероприятие нельзя перевести в статус `closed`, если у него есть хотя бы одна транзакция с `paymentMethod = obligation`.
3. Пользователь должен получить понятное предупреждение:
   - в самой транзакции и связанных списках;
   - при попытке закрыть мероприятие.
4. Для завершения обязательства пользователь должен:
   - открыть транзакцию;
   - сменить метод оплаты на любой обычный;
   - указать фактическую дату совершения;
   - сохранить изменения.

## Изменения в API и серверной валидации

### Транзакции

Файлы уровня API транзакций:

- `app/api/transactions/route.js`
- `app/api/transactions/[id]/route.js`
- `schemas/transactionsSchema.js`

Изменения:

- добавить `obligation` в список допустимых `paymentMethod`;
- разрешить создание и редактирование транзакций с таким методом;
- не менять правила расчёта суммы, типа, категории и связи с мероприятием/клиентом.

### Закрытие мероприятия

Файл:

- `app/api/events/[id]/route.js`

Перед сохранением `status = 'closed'` сервер должен проверять наличие транзакций:

- `tenantId = текущий tenant`
- `eventId = текущее мероприятие`
- `paymentMethod = 'obligation'`

Если такие транзакции есть, сервер возвращает `409` и текст ошибки по смыслу:

`Нельзя закрыть мероприятие: есть транзакции с обязательствами. Переведите их на другой метод оплаты и укажите фактическую дату совершения.`

Серверная проверка является обязательной и считается источником истины, даже если клиент уже пытается предупредить пользователя заранее.

## Изменения в интерфейсе

### Форма транзакции

Файл:

- `layouts/modals/modalsFunc/transactionFunc.js`

Поведение:

- в блок выбора методов оплаты добавляется кнопка `Обязательство`;
- если выбран `Обязательство`, рядом с полем даты показывается пояснение, что сейчас это плановая дата;
- если пользователь редактирует транзакцию и переводит её с `obligation` на обычный метод оплаты, интерфейс должен явно напоминать, что дата теперь должна стать фактической;
- сохранение должно использовать ту дату, которую пользователь указал вручную.

Форма не должна автоматически подменять дату без явного действия пользователя при смене метода с `obligation`.

### Карточки и списки транзакций

Файлы:

- `layouts/cards/TransactionCard.js`
- связанные списки/модалки, где рендерятся данные транзакции

Изменения:

- показывать заметный бейдж `Обязательство`, если `paymentMethod = obligation`;
- для таких транзакций подпись даты должна явно указывать, что это плановая дата;
- визуально такие транзакции должны быть различимы без открытия карточки.

### Просмотр мероприятия и закрытие

Файлы:

- `state/itemsFuncGenerator.js`
- модальный поток закрытия мероприятия;
- при необходимости `layouts/modals/modalsFunc/eventViewFunc.js`

Изменения:

- если сервер вернул `409` из-за обязательств, пользователь должен увидеть осмысленное сообщение без технических деталей;
- в просмотре мероприятия желательно показать предупреждающий блок, если у мероприятия есть транзакции с методом `obligation`, чтобы проблема была видна до попытки закрытия.

## Расчёты и статистика

Отдельная логика для статистики не добавляется.

Обоснование:

- текущая модель считает транзакции по сумме, типу и категории;
- новый метод оплаты не должен исключать транзакцию из агрегатов;
- требование пользователя прямо говорит учитывать обязательство как полноценную транзакцию.

Следовательно, если в коде нет мест, где список методов оплаты жёстко ограничивает выборку для статистики, бизнес-логика расчётов остаётся без изменений.

## Тестирование

Перед реализацией и во время неё нужно покрыть следующие сценарии:

1. Создание транзакции с `paymentMethod = obligation`.
2. Обновление существующей транзакции с установкой `paymentMethod = obligation`.
3. Перевод транзакции с `obligation` на обычный метод оплаты с сохранением новой даты.
4. Попытка закрыть мероприятие при наличии хотя бы одной транзакции с `paymentMethod = obligation` должна завершаться ошибкой `409`.
5. Закрытие мероприятия без обязательств должно работать как раньше.

## Границы и допущения

- Изменения выполняются только в `ArtistCRM`.
- Миграция существующих данных не требуется.
- Старые транзакции не меняются автоматически.
- Новое поведение не должно менять существующие категории транзакций.
- Если в интерфейсе уже есть локальные вычисления по методам оплаты, они должны быть только расширены новым значением, а не переписаны целиком.

## Результат

После внедрения пользователь сможет заносить запланированные финансовые обязательства как обычные транзакции, видеть их в финансовой картине, но не сможет закрыть мероприятие, пока такие обязательства не будут фактически исполнены и переведены в обычный способ оплаты с корректной датой совершения.
