# Библиотека шаблонов документов и единый блок документов мероприятия

## Контекст

В ArtistCRM уже есть формирование договора и акта в `.docx` из пользовательских или стандартных шаблонов. Сейчас пользователь может загрузить только два фиксированных шаблона: договор и акт. В редакторе мероприятия есть отдельные действия `Сформировать договор` и `Сформировать акт`, а документы мероприятия разложены по разным полям: `contractLinks`, `actLinks`, `documentFiles`.

Новая цель: дать пользователю возможность загрузить несколько собственных DOCX-шаблонов, назвать их понятным образом и выбирать нужный шаблон при формировании документа под мероприятие. Дополнительно нужно упростить блок документов мероприятия: ссылки и файлы должны храниться как именованные документы с типом.

## Цели

- Пользователь сам загружает нужные DOCX-шаблоны в настройках кабинета.
- Каждый шаблон имеет свободное название и системный тип: `Договор`, `Счет`, `Чек`, `Акт`, `Другое`.
- В редакторе мероприятия пользователь выбирает шаблон и формирует `.docx`.
- Сгенерированный документ скачивается на устройство, как сейчас; после этого пользователь может прикрепить файл или ссылку к мероприятию.
- В мероприятии появляется единый блок `Документы мероприятия` вместо отдельных списков договоров, актов и файлов.
- При добавлении ссылки или файла пользователь выбирает тип документа и задает название, если выбран тип `Другое`.
- Интерфейс сохраняет текущую стилистику ArtistCRM: компактные блоки, существующие компоненты, phone-first компоновка.

## Не цели

- Не делать серверную генерацию и автоматическое сохранение DOCX-файла в CRM на первом этапе.
- Не создавать универсальные шаблоны для всех пользователей на первом этапе.
- Не переносить шаблоны в отдельную Mongo-модель, пока объем и число пользователей невелики.
- Не менять формат переменных DOCX сверх уже поддерживаемых тегов.

## Модель данных

### Шаблоны документов

Шаблоны хранятся в `SiteSettings.custom.documentTemplates[]`.

```js
{
  id: 'uuid',
  name: 'Договор ИП',
  type: 'contract', // contract | invoice | receipt | act | other
  customTypeName: '',
  fileName: 'dogovor-ip.docx',
  templateBase64: '...',
  createdAt: '2026-07-03T00:00:00.000Z',
  updatedAt: '2026-07-03T00:00:00.000Z'
}
```

Типы:

- `contract` - договор;
- `invoice` - счет;
- `receipt` - чек;
- `act` - акт;
- `other` - другое, с пользовательским `customTypeName`.

Legacy-поля `contractDocxTemplateBase64`, `contractDocxTemplateFileName`, `actDocxTemplateBase64`, `actDocxTemplateFileName` должны быть учтены при переходе. Реализация переносит их в первые элементы `documentTemplates[]` в миграции настроек, а клиентская нормализация используется только как временная страховка до запуска миграции.

### Документы мероприятия

В событии добавляется единый массив `documents[]`.

```js
{
  id: 'uuid',
  type: 'contract', // contract | invoice | receipt | act | other
  title: 'Договор',
  url: 'https://disk.yandex.ru/i/example',
  file: null,
  createdAt: '2026-07-03T00:00:00.000Z'
}
```

Для прикрепленного файла используется та же структура:

```js
{
  id: 'uuid',
  type: 'act',
  title: 'Акт',
  url: '',
  file: {
    name: 'akt-12.docx',
    url: 'https://...',
    path: 'events/.../documents/akt-12.docx',
    size: 12345,
    contentType: 'application/vnd.openxmlformats-officedocument.wordprocessingml.document'
  },
  createdAt: '2026-07-03T00:00:00.000Z'
}
```

Legacy-поля `contractLinks`, `actLinks`, `documentFiles` остаются в схеме на переходный период, но новый UI и API должны писать только `documents[]`.

## UX

### Страница `Документы`

Текущие две карточки `DOCX-шаблон договора` и `DOCX-шаблон акта` заменяются на список `Шаблоны документов`.

Основные действия:

- `Добавить шаблон`;
- `Заменить файл`;
- `Переименовать / изменить тип`;
- `Удалить`;
- `Скачать стандартный шаблон договора`;
- `Скачать стандартный шаблон акта`;
- `Открыть инструкцию DOCX`;
- `Редактировать реквизиты`.

Модалка добавления/редактирования шаблона:

- `Название`;
- `Тип документа`;
- `Название типа`, если выбран `Другое`;
- загрузка `.docx`.

### Редактор мероприятия

В табе `Финансы и Документы` вместо отдельных кнопок договора и акта появляется блок `Сформировать документ`.

Поля блока:

- выбор шаблона;
- номер документа;
- дата документа;
- кнопка `Скачать Word (.docx)`.

Номер по умолчанию ведется отдельно по типам через настройки:

- `contractLastNumber`;
- `actLastNumber`;
- `invoiceLastNumber`;
- `receiptLastNumber`;
- `otherLastNumber`.

Для `other` используется общий счетчик `otherLastNumber`. Если у конкретного шаблона в будущем потребуется своя нумерация, это отдельная доработка.

Ниже располагается единый блок `Документы мероприятия`.

Действия:

- `Добавить ссылку`;
- `Прикрепить файл`.

При добавлении ссылки или файла пользователь выбирает тип документа: `Договор`, `Счет`, `Чек`, `Акт`, `Другое`. Для `Другое` вводит название. Для стандартных типов поле названия можно предзаполнить выбранным типом, но оставить редактируемым.

## API и валидация

- `POST /api/site` продолжает сохранять `custom.documentTemplates[]`.
- `POST /api/events` и `PATCH /api/events/[id]` принимают `documents[]`.
- Защита и tenant-aware поведение остаются через существующие `getTenantContext()` и фильтры по `tenantId`.
- Если тариф не разрешает `allowDocuments`, API не должен принимать `documents[]`, как сейчас не принимает документы.
- Если событие имеет статус `draft`, сохраняется текущее правило: документы недоступны для заявки. Новый `documents[]` должен блокироваться так же, как legacy-документы.
- Загружаемый DOCX-шаблон ограничивается 5 МБ до base64-кодирования. Проверка нужна на клиенте для понятной ошибки и на сервере для защиты данных.
- Формат ошибок должен остаться в существующем JSON-стиле проекта.

## Миграция

Нужен одноразовый идемпотентный скрипт, например `scripts/migrate-event-documents.js`.

Алгоритм:

1. Найти события, где есть `contractLinks`, `actLinks` или `documentFiles`.
2. Считать существующий `documents[]`, если он уже есть.
3. Добавить отсутствующие документы:
   - `contractLinks[]` -> `documents[]` с `type: 'contract'`, `title: 'Договор'`, `url`;
   - `actLinks[]` -> `documents[]` с `type: 'act'`, `title: 'Акт'`, `url`;
   - `documentFiles[]` -> `documents[]` с `type: 'other'`, `title` из имени файла или `Документ`, `file`.
4. Не плодить дубли при повторном запуске. Ключ дедупликации: `type + url` для ссылок и `file.path || file.url || file.name` для файлов.
5. Не удалять legacy-поля сразу, чтобы сохранить возможность отката и проверки.

В тот же переходный пакет входит миграция настроек:

1. Если `custom.documentTemplates[]` пустой, но есть legacy DOCX-шаблон договора, создать шаблон `Договор` с `type: 'contract'`.
2. Если есть legacy DOCX-шаблон акта, создать шаблон `Акт` с `type: 'act'`.
3. Не удалять legacy-поля сразу.

## Обратная совместимость

- Новый UI пишет только `documents[]`.
- На переходный период чтение нормализует legacy-документы в памяти, если `documents[]` отсутствует.
- Старые поля шаблонов показываются как элементы библиотеки до миграции.
- После успешной миграции и стабилизации отдельной задачей удаляются legacy UI-ветки и поля.

## Тестирование

- Unit-тест нормализации документов мероприятия из `contractLinks`, `actLinks`, `documentFiles` в `documents[]`.
- Unit-тест идемпотентности миграции legacy-документов.
- Unit-тест нормализации legacy DOCX-шаблонов в `documentTemplates[]`.
- Точечный `eslint` по измененным JS-файлам.
- Ручная проверка mobile-first:
  - список шаблонов на странице `Документы`;
  - добавление, замена, переименование и удаление шаблона;
  - выбор шаблона и скачивание DOCX в мероприятии;
  - добавление ссылки с типом и названием;
  - прикрепление файла с типом и названием.

## Решения для реализации

- Нормализация документов и шаблонов размещается в отдельных helper-файлах в `helpers/`, чтобы переиспользовать ее в UI, API, миграциях и тестах.
- Лимит размера DOCX-шаблона: 5 МБ до base64-кодирования, с одинаковой проверкой на клиенте и сервере.
- `.superpowers/` добавляется в `.gitignore`, так как visual companion создает локальные макеты в этом каталоге.
