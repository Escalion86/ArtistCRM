# Дизайн: автосохранение мероприятия перед добавлением транзакции

## Контекст

В редакторе события пользователь может открыть существующую заявку (`status: draft`), переключить тип на `Мероприятие` (`status: active`) и сразу перейти в финансовый блок. Сейчас UI уже показывает секцию транзакций по локальному статусу формы, но действие `Добавить транзакцию` опирается на сохраненное состояние записи и `eventId`. В результате пользователь получает ошибку уровня заявки или требование сначала вручную сохранить форму.

Это создает лишний шаг в одном из частых сценариев: заявка дозаполняется и сразу переводится в рабочее мероприятие с фиксацией предоплаты или другой первой транзакции.

## Цель

Убрать необходимость отдельного ручного сохранения между переключением `Заявка -> Мероприятие` и добавлением первой транзакции.

После выбора типа `Мероприятие` кнопка `Добавить транзакцию` должна:

1. при необходимости автоматически сохранить текущую форму события;
2. после успешного сохранения сразу открыть модалку транзакции;
3. сохранить текущий запрет на транзакции для настоящих заявок (`draft`).

## Подходы

### 1. Автосохранение при клике на `Добавить транзакцию`

Рекомендованный вариант.

Поведение:
- если локальный статус формы `draft`, показывается текущий запрет на транзакции;
- если локальный статус формы уже не `draft`, но событие еще не сохранено в актуальном виде, кнопка запускает сохранение;
- после успешного сохранения открывается стандартная модалка транзакции с реальным `eventId`.

Плюсы:
- минимальные изменения в текущей архитектуре;
- повторное использование существующего `setEvent`;
- не требует временных транзакций без `eventId`;
- хорошо ложится в текущий mobile-first поток.

Минусы:
- действие становится составным, поэтому нужно явно блокировать повторные клики и аккуратно показывать ошибку сохранения.

### 2. Отдельная кнопка `Сохранить и добавить транзакцию`

Не рекомендуется.

Плюсы:
- максимально явное поведение.

Минусы:
- перегружает интерфейс;
- дублирует уже существующее действие;
- хуже подходит для компактной мобильной формы.

### 3. Буферизация транзакции до сохранения события

Не рекомендуется.

Плюсы:
- самый "магический" и плавный UX.

Минусы:
- требует отдельной временной модели данных;
- повышает риск рассинхрона между формой события и транзакцией;
- заметно дороже по сложности и тестированию.

## Решение

Выбрать подход 1: автосохранение события перед открытием модалки транзакции.

## UX-поток

### Сценарий A: настоящая заявка

Условия:
- локальный `status === 'draft'`.

Поведение:
- `Добавить транзакцию` не открывает модалку;
- пользователь видит существующее сообщение `Транзакции недоступны для заявки`.

### Сценарий B: заявка переведена в мероприятие в текущей форме

Условия:
- локальный `status !== 'draft'`;
- форма содержит несохраненные изменения или запись еще не существует в сохраненном виде для текущего состояния;
- транзакция открывается из редактора события.

Поведение:
1. пользователь нажимает `Добавить транзакцию`;
2. форма блокирует повторные нажатия на время операции;
3. событие сохраняется через тот же payload, что и обычное сохранение формы;
4. после успешного сохранения:
   - локальная форма продолжает работать уже с сохраненным событием;
   - открывается стандартная модалка создания транзакции;
5. при ошибке сохранения:
   - модалка транзакции не открывается;
   - в финансовом блоке показывается ошибка сохранения события.

### Сценарий C: уже сохраненное мероприятие

Условия:
- локальный `status !== 'draft'`;
- сохранение не требуется.

Поведение:
- модалка транзакции открывается сразу, как и сейчас.

## Технический дизайн

Изменения должны оставаться локальными для [eventFunc.js](/d:/Programming/Projects/ArtistCRM_PartyCRM/ArtistCRM/layouts/modals/modalsFunc/eventFunc.js:1).

### 1. Переиспользуемое сохранение события

Текущую логику сборки payload и вызова `setEvent` нужно вынести в локальный helper внутри модалки события.

Требования к helper:
- использует тот же набор валидаций, что и обычное сохранение;
- возвращает сохраненный объект события;
- умеет работать и для обычного confirm-сохранения, и для автосохранения перед транзакцией;
- не дублирует вторичную post-save логику в разных местах без необходимости.

### 2. Ветка автосохранения в `openTransactionModal`

`openTransactionModal` должен определять:
- запрещен ли сценарий из-за `draft`;
- нужен ли save-before-open;
- можно ли открыть транзакцию сразу.

Когда save-before-open нужен, функция должна:
- включать локальный loading для финансового блока;
- вызывать helper сохранения;
- брать `savedEvent._id` и `savedEvent.contractSum`;
- открывать `modalsFunc.transaction?.add(savedEvent._id, { contractSum: savedEvent.contractSum })`.

### 3. Синхронизация локального состояния после автосохранения

После успешного автосохранения редактор не должен оставаться в "полунесохраненном" состоянии.

Минимальное требование:
- форма должна опираться на уже обновленные query/state данные либо на возвращенный `savedEvent` так, чтобы повторное нажатие не пыталось снова сохранять ту же версию без причины.

Практический ориентир:
- использовать тот же путь обновления, который уже применяется при обычном `setEvent`, без ввода нового отдельного слоя состояния.

### 4. Ошибки и блокировки

Нужно сохранить предсказуемое поведение:
- во время автосохранения кнопка добавления транзакции и кнопки удаления/редактирования транзакций блокируются;
- ошибка сохранения показывается в `financeError`;
- модалка транзакции не открывается при ошибке.

## Ограничения

- Не менять контракт API транзакций.
- Не разрешать создание транзакций для `draft`.
- Не вводить временные локальные транзакции без `eventId`.
- Не добавлять новые кнопки в UI, если текущий поток можно улучшить автоматически.

## Проверка

Нужно покрыть как минимум ручную проверку сценариев:

1. Открыть существующую заявку, переключить на `Мероприятие`, нажать `Добавить транзакцию`:
   ожидается автосохранение и открытие модалки транзакции.
2. Повторить сценарий при ошибке валидации или ошибке сохранения:
   ожидается, что транзакция не откроется и появится понятная ошибка.
3. Открыть обычную заявку без смены статуса:
   ожидается текущий запрет на транзакции.
4. Открыть уже сохраненное мероприятие:
   ожидается мгновенное открытие модалки транзакции без промежуточного сохранения.

## Риски

- Случайное дублирование побочных эффектов обычного `handleSave`, если логика сохранения будет вынесена неаккуратно.
- Повторное открытие транзакции или повторный save при двойном клике, если не поставить блокировку.
- Регрессии в post-save сценариях мероприятия, если helper сохранения затронет существующие confirm-flow ветки.
