# First Run Wizard And Event Statuses Design

## Контекст

Текущий первый запуск раздроблен: обязательный профиль открывается отдельной модалкой, а `ReleaseOnboardingCoach` работает как floating-чеклист после входа. Для нового пользователя это выглядит не как цельный мастер настройки, а как набор подсказок.

Новая цель - полностью заменить текущий мастер настройки единым модальным wizard первого запуска. Он должен последовательно собрать важные данные, объяснить базовую модель карточек и включить только нужные пользователю опции.

Отдельно нужно изменить пользовательское название статуса `active`: вместо `Мероприятие` показывать `Подтверждено`. Кодовое значение `active` остается неизменным для совместимости БД, API, календаря, статистики и мобильного клиента.

## Целевой Подход

Реализовать новый модальный мастер первого входа и убрать текущий floating-мастер `ReleaseOnboardingCoach` из первого запуска.

Wizard должен открываться автоматически после регистрации/первого входа, если настройка завершения еще не сохранена. Закрытие крестиком или пропуск обязательных шагов не должно оставлять пользователя в неконсистентном состоянии: обязательные шаги должны блокировать переход дальше, необязательные можно пропустить.

## Поток Wizard

### Шаг 1. Профиль

Собираем основные данные пользователя:

- фото;
- имя;
- фамилия;
- отчество, если уже поддерживается формой пользователя;
- телефон;
- WhatsApp;
- Telegram;
- VK;
- Instagram.

Минимально обязательные поля: имя и фамилия. Телефон желательно попросить, но не блокировать, если текущая модель авторизации уже хранит телефон или пользователь вошел через внешний провайдер без ручного ввода.

Фото необязательно. Если пользователь его не загрузил, wizard продолжает работу.

### Шаг 2. Внешний Вид И Базовые Настройки

Собираем:

- тема: светлая или темная;
- основной город;
- список городов, если пользователь хочет добавить несколько;
- часовой пояс.

Город и часовой пояс нужны для корректных дат, напоминаний, календаря и будущих уведомлений. После сохранения выставляется существующий флаг `timeZoneConfirmed`.

### Шаг 3. Специализация И Услуги

Пользователь выбирает специализацию из пресетов, аналогично текущему onboarding:

- мероприятия и сцена;
- фото, видео, контент;
- изделия и заказы;
- красота и персональные услуги;
- консультации и обучение;
- другое / настрою сам.

После выбора специализации wizard предлагает стартовые услуги из пресета.

Если у пользователя уже есть созданные услуги, автоматическое создание услуг из пресета не предлагается. Вместо этого показывается предупреждение:

> Вижу, что у вас уже есть созданные услуги. Создание новых услуг из пресета может испортить вашу структуру, поэтому лучше добавьте или поправьте услуги вручную.

Пользователь может перейти в ручное добавление/редактирование услуг.

Группы услуг объясняются коротко: группа - это полка, услуга - конкретное предложение. Группы не являются обязательным шагом первого запуска.

### Шаг 4. Передача Заказа Коллеге

Wizard задает вопрос:

> Бывает ли, что вы передаете заказ коллеге?

Если пользователь отвечает `Да`, сохраняем настройку, что пользователь иногда передает заказы коллеге.

Технически новая модель передачи не нужна: в проекте уже существуют поля события:

- `isTransferred`;
- `colleagueId`.

Новая настройка управляет только видимостью этих полей в редакторе заявки/мероприятия:

- если настройка включена, в редакторе видны существующие `Передано коллеге` и выбор коллеги;
- если настройка выключена, эти поля скрыты;
- если у уже существующего события `isTransferred === true`, просмотр карточки и статистика продолжают показывать передачу корректно.

Рекомендуемый ключ настройки: `siteSettings.custom.showColleagueTransferFields`.

Важно: скрытие полей в редакторе не должно автоматически сбрасывать `isTransferred` и `colleagueId` у старых событий. Сброс возможен только если пользователь явно редактирует карточку и отключает передачу при видимых полях.

### Шаг 5. Объяснение Статусов Карточек

Wizard объясняет четыре пользовательских статуса:

- `Заявка` (`draft`) - клиент проявил интерес, но заказ еще не подтвержден. Главная задача: поставить следующий контакт.
- `Подтверждено` (`active`) - клиент подтвердил заказ, дату или условия. Это уже рабочая карточка, которую нужно вести по оплатам, задачам, документам и календарю.
- `Отменено` (`canceled`) - заказ не состоялся и не должен считаться активной работой.
- `Закрыто` (`closed`) - работа завершена, оплаты и документы доведены до конца.

Во всех пользовательских местах label `Мероприятие` для `active` нужно заменить на `Подтверждено`, где речь идет именно о статусе. При этом слово "мероприятие" можно оставить в нейтральных местах, где оно означает сущность/заказ/карточку, а не статус.

Кодовое значение `active` не переименовывается.

### Шаг 6. Финал

Финальный экран:

- благодарит пользователя за регистрацию;
- коротко сообщает, что базовая настройка завершена;
- объясняет, что подробнее ознакомиться со всеми возможностями и настройками можно в блоке меню `Настройки`;
- предлагает перейти в кабинет.

После завершения сохраняется флаг завершения нового wizard.

## Что Убрать

Текущий floating-мастер запуска нужно убрать из сценария первого входа.

Допустимо оставить ручной повторный запуск нового wizard из `Настройки`, но старый `ReleaseOnboardingCoach` не должен показываться автоматически после первого входа.

Старые ключи `releaseOnboardingCompleted` и `releaseOnboardingShowToken` можно сохранить для обратной совместимости, но новый wizard должен иметь собственный явный флаг завершения, например `siteSettings.custom.firstRunWizardCompleted`.

## Данные

Минимальные настройки в `siteSettings.custom`:

- `firstRunWizardCompleted`: новый wizard завершен;
- `firstRunWizardCompletedAt`: дата завершения;
- `onboardingActivityPreset`: выбранная специализация, уже используется текущим onboarding;
- `onboardingStarterServicesCreated`: стартовые услуги созданы из пресета;
- `onboardingStarterServicesManual`: пользователь решил настроить услуги вручную;
- `showColleagueTransferFields`: показывать поля передачи заказа коллеге;
- `timeZoneConfirmed`: часовой пояс подтвержден, уже используется.

Профильные данные сохраняются в существующую модель пользователя. Город, города и часовой пояс сохраняются в существующие настройки сайта/кабинета.

## Компоненты И Зоны Изменений

Ожидаемые зоны реализации:

- `layouts/modals/modalsFunc/userOnboardingFunc.js` - заменить старую профильную модалку или превратить ее в шаг нового wizard.
- `components/ReleaseOnboardingCoach.js` - убрать из автопоказа первого запуска или заменить на новый wizard-компонент.
- `components/StateLoader.js` - изменить условие автопоказа onboarding.
- `helpers/onboardingPresets.mjs` - переиспользовать пресеты специализаций и стартовые услуги.
- `layouts/modals/modalsFunc/eventFunc.js` - скрывать/показывать `Передано коллеге` и `ColleaguePicker` по `siteSettings.custom.showColleagueTransferFields`, сохраняя видимость для уже переданных карточек при необходимости.
- `helpers/constants.js`, `components/GoogleCalendarSettings.js`, `layouts/content/EventsContent.js`, `layouts/cards/EventCard.js`, `layouts/modals/modalsFunc/eventViewFunc.js`, `layouts/content/StatisticsContent.js` и похожие места - заменить пользовательский label статуса `active` с `Мероприятие` на `Подтверждено`, не меняя значение `active`.
- `layouts/content/SettingsContent.js` - добавить настройку "Иногда передаю заказы коллеге" и ручной запуск нового wizard.

## Обработка Ошибок

- Если профильные данные не сохранились, пользователь остается на шаге профиля и видит ошибку.
- Если город/часовой пояс не сохранились, пользователь остается на шаге базовых настроек.
- Если услуги из пресета не создались, wizard показывает ошибку и предлагает настроить услуги вручную.
- Если у пользователя уже есть услуги, wizard не создает пресетные услуги автоматически.
- Если настройка передачи коллеге не сохранилась, пользователь может повторить сохранение или пропустить шаг, при этом по умолчанию поля передачи скрыты.

## Совместимость

- Не менять enum статусов в БД и API.
- Не переименовывать `active`.
- Не менять смысл `isTransferred` и `colleagueId`.
- Не сбрасывать существующие передачи коллеге при выключенной новой настройке.
- Не ломать текущие фильтры, статистику, Google Calendar sync и импорт.
- Mobile-first: все шаги wizard должны быть удобны на телефоне.

## Тестирование

Минимальные проверки:

- новый пользователь видит новый модальный wizard вместо старого floating-мастера;
- шаг профиля сохраняет данные пользователя;
- шаг темы/города/часового пояса сохраняет `siteSettings` и `timeZoneConfirmed`;
- выбор специализации сохраняет пресет;
- услуги из пресета создаются только если услуг еще нет;
- при существующих услугах показывается предупреждение и ручной путь;
- настройка `showColleagueTransferFields` включает поля передачи коллеге в `eventFunc`;
- при выключенной настройке поля передачи скрыты в редакторе;
- существующие переданные карточки продолжают отображаться в просмотре и статистике;
- статус `active` отображается пользователю как `Подтверждено`;
- API payload, БД и фильтры продолжают использовать `active`;
- wizard завершается, сохраняет `firstRunWizardCompleted` и больше не открывается автоматически;
- ручной повторный запуск из настроек работает.

## Не Входит В Эту Задачу

- Переименование сущности `event` в коде.
- Миграция `active` в новый enum.
- Новая модель передачи коллеге.
- Полноценный учебный курс по всем настройкам.
- Изменение публичных API входящих заявок.
