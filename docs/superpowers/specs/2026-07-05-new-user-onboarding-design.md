# New User Onboarding Design

## Контекст

Текущий `ReleaseOnboardingCoach` помогает пройти первые действия, но слишком кратко объясняет продуктовую модель. Новому пользователю непонятны различия между статусами `Заявка`, `Мероприятие` и `Закрыто`, а настройка услуг с группами выглядит сложнее, чем нужно для старта.

Цель изменения - снизить порог входа: пользователь должен за первые минуты понять, как ArtistCRM помогает не терять заявки, помнить следующий контакт, фиксировать подтвержденные заказы и закрывать завершенные работы.

## Целевой Подход

Выбран гибрид обучающего мини-тура и опциональной учебной заявки.

Мастер должен:

- объяснять базовую логику CRM на языке пользователя;
- персонализировать примеры через выбранный вид деятельности;
- предлагать стартовый набор услуг из пресета;
- объяснять группы услуг как необязательную сортировку "на потом";
- предлагать создать учебную заявку, но не навязывать ее;
- закреплять привычку указывать следующий контакт или следующее действие.

## Пресеты Деятельности

На первом запуске пользователь выбирает ближайший вид деятельности:

- `events`: мероприятия и сцена - ведущий, артист, DJ, музыкант, группа, шоу-программа;
- `photo_video`: фото, видео, контент;
- `custom_products`: изделия и заказы - торты, декор, подарки, одежда, ручная работа;
- `beauty`: красота и персональные услуги;
- `consulting`: консультации и обучение;
- `other`: другое / настрою сам.

Пресет не должен менять основную бизнес-логику. Он нужен для стартовых текстов, примеров услуг и учебной заявки. Значение можно хранить в `siteSettings.custom`, чтобы не добавлять обязательную схему на первом этапе.

## Поток Мастера

1. Профиль

   Пользователь заполняет имя, фамилию, город, часовой пояс и тему. Этот шаг уже существует, но текст должен объяснять, зачем нужны город и часовой пояс: корректные даты, напоминания и календарь.

2. Вид деятельности

   Пользователь выбирает пресет. Для `other` мастер использует нейтральные формулировки: "заказ", "услуга", "клиент", "дата".

3. Услуги

   Мастер предлагает 2-4 стартовые услуги из выбранного пресета. Пользователь может создать их как есть, переименовать или пропустить.

   Рекомендация в интерфейсе: начать с 1-3 основных услуг. Группы не обязательны; они нужны, когда список услуг станет большим. Формулировка: "Группа - это полка, услуга - конкретное предложение".

4. Логика CRM

   Мастер объясняет статусы:

   - `Заявка`: клиент проявил интерес, но еще не подтвердил заказ. Важно зафиксировать следующий контакт.
   - `Мероприятие`: клиент подтвердил заказ, дату или условия. Это уже работа в календаре и финансах.
   - `Закрыто`: работа завершена, оплаты и документы доведены до конца. Закрытое событие не требует дальнейших действий.
   - `Отменено`: заказ не состоялся и не должен считаться активной работой.

5. Учебная заявка

   Мастер предлагает создать учебную заявку по выбранному пресету. Это opt-in действие: основная кнопка "Создать учебную заявку", вторичная - "Пропустить".

   Если пользователь соглашается, заявка должна быть явно помечена как учебная и иметь быстрый способ удаления. Учебная заявка должна показывать путь: заявка -> мероприятие -> закрыто.

6. Следующий контакт

   Мастер объясняет центральную привычку: у каждой новой заявки должен быть следующий шаг. Примеры: "перезвонить завтра", "уточнить решение", "получить задаток", "подготовить договор".

## Компоненты

- `ReleaseOnboardingCoach`: расширить из короткого чеклиста в пошаговый мастер быстрого старта.
- `userOnboardingFunc`: оставить как обязательный профильный шаг, но тексты сделать более объясняющими.
- Новый модуль пресетов: отдельный helper с описанием видов деятельности, стартовых услуг и учебных заявок.
- Механика создания учебной заявки: использовать существующие event/service CRUD-пути, не дублировать серверную логику.

## Данные

Минимальные новые данные:

- `siteSettings.custom.onboardingActivityPreset`: выбранный пресет;
- `siteSettings.custom.releaseOnboardingCompleted`: уже используется;
- `siteSettings.custom.releaseOnboardingShowToken`: уже используется.

Для учебной заявки нужен признак, позволяющий отличить ее от реальных данных. Предпочтительный вариант - не добавлять отдельное поле в схему на первом этапе, а использовать безопасный маркер в существующих данных только если это не ломает UX. Если для чистого удаления и фильтрации потребуется надежная модель, добавить явное поле `isDemo` в события и учитывать его только в onboarding-сценариях.

## Обработка Ошибок

- Если стартовые услуги не создались, мастер должен показать ошибку и предложить продолжить вручную через "Мои услуги".
- Если учебная заявка не создалась, мастер не должен блокировать пользователя; нужно показать сообщение и оставить кнопку повторной попытки.
- Если пользователь уже создал реальные услуги или заявки, мастер не должен навязывать пресетные данные, а должен отметить соответствующие шаги выполненными.
- Если пользователь пропустил учебную заявку, мастер считается валидно пройденным после объяснения статусов и следующего контакта.

## Тестирование

Проверить точечно:

- новый пользователь проходит профиль, выбирает пресет, создает предложенные услуги;
- пользователь выбирает `other` и получает нейтральные тексты;
- пользователь пропускает создание учебной заявки;
- пользователь создает учебную заявку и видит ее в списке;
- учебная заявка удаляется без затрагивания реальных данных;
- существующий пользователь с услугами и заявками не получает лишние пресетные данные;
- мастер корректно работает на мобильной ширине.

Для реализации достаточно точечного `eslint` по измененным JS-файлам и ручной проверки основного onboarding-потока. Если будет добавлен helper пресетов, для него стоит сделать небольшие unit-тесты нормализации.

## Не Входит В Первый Этап

- Полная система шаблонов для всех ниш.
- Изменение названия продукта или глобального позиционирования.
- Автоматическое создание групп услуг как обязательного шага.
- Обязательная миграция существующих пользователей на новый пресет.
- Изменение публичных API входящих заявок.
